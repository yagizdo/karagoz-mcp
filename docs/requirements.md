# Requirements

What each command needs on your computer and on the device, and how karagoz finds `adb` and Xcode.

- **Node 22 or newer.**
- **`adb`** from Android platform-tools, for Android targets. karagoz does not bundle it; it looks for it on every run, in this order:
  1. `$ANDROID_HOME/platform-tools/adb`
  2. `$ANDROID_SDK_ROOT/platform-tools/adb`
  3. `adb` on `PATH`
  4. Android Studio's default SDK: `~/Library/Android/sdk` on macOS, `~/Android/Sdk` on Linux, `%LOCALAPPDATA%\Android\Sdk` on Windows

  An empty variable is skipped. The first `adb` that starts is used for the rest of the run, so a broken `adb` under `ANDROID_HOME` does not fall back to `PATH`. The exception is an `adb` that fails to start with `ENOENT` (a missing interpreter or a broken link): it counts as not there, and the next one is tried. Under `karagoz mcp` the run is the whole server session, and if the `adb` in use disappears (`ENOENT`), the next call looks it up again. An `adb` that appears mid-session higher in the list is not picked up until the server restarts. [`karagoz doctor`](commands/doctor.md) shows which one is used and why. `install` needs platform-tools 30.0.0 or newer. When none is found:

  ```json
  {"error":{"code":"ADB_NOT_FOUND","message":"adb not found (tried ..., PATH). Install platform-tools (brew install --cask android-platform-tools, or download https://developer.android.com/tools/releases/platform-tools and add it to PATH) or set ANDROID_HOME to your Android SDK."}}
  ```

- **A running emulator** (`emulator -avd <name>`), or for `devices`, `screenshot`, `ui-tree`, `tap`, `swipe`, `text`, `key`, `install`, `launch`, `terminate`, `uninstall` and `logs`, a phone with USB debugging on, in state `device`, or for `devices`, `screenshot`, `ui-tree`, `tap`, `swipe`, `text`, `key`, `install`, `launch`, `terminate`, `uninstall` and `logs` on macOS, a booted iOS simulator (`open -a Simulator`; on Xcode 27, `xcrun simctl boot <name>`), or for every command on macOS, an iPhone connected to the Mac (for `screenshot`, `install`, `launch`, `terminate` and `uninstall`, paired with the Mac and with Developer Mode on: Settings > Privacy & Security > Developer Mode; for `logs`, paired and connected by USB cable; for `ui-tree`, `tap`, `swipe`, `text` and `key`, also connected by USB cable, Settings > Developer > Enable UI Automation on, and karagoz's runner installed with [`install-runner`](commands/install-runner.md)). A phone that adb cannot see is missing from the list: on Windows without the phone maker's USB driver, on a Mac laptop where "Allow accessory to connect" was refused, or in fastboot mode.
- For `ui-tree` and `tap --text` / `--id`: the screen is on, and no other UiAutomation client is connected (Appium, Maestro, `uiautomator events`). For input to reach apps, the screen is also unlocked: on a lock screen `text` and `key` type into the PIN field, and a wrong PIN counts as a failed unlock attempt; with the screen off, taps are dropped and keys still arrive. Both exit `0`.
- **Xcode, opened once**, for iOS simulators in `devices`, `screenshot`, `ui-tree`, `tap`, `swipe`, `text`, `key`, `install`, `launch`, `terminate`, `uninstall` and `logs` (macOS only). karagoz runs CoreSimulator's own `simctl` (`/Library/Developer/PrivateFrameworks/CoreSimulator.framework/Versions/A/Resources/bin/simctl`), or `$DEVELOPER_DIR/usr/bin/simctl` when `DEVELOPER_DIR` is set. The Command Line Tools alone have no `simctl`, and no `swiftc` for the helper below. For iPhones in `devices`, `install`, `launch`, `terminate`, `uninstall` and `logs`, Xcode 15 or newer: karagoz runs CoreDevice's own `devicectl` (`/Library/Developer/PrivateFrameworks/CoreDevice.framework/Versions/A/Resources/bin/devicectl`), or `$DEVELOPER_DIR/usr/bin/devicectl` when `DEVELOPER_DIR` is set; the Command Line Tools alone have none. For `screenshot` on an iPhone, Xcode 27 or newer, opened once: Xcode 26's `devicectl` has no `device capture screenshot`. For `ui-tree`, `tap`, `swipe`, `text` and `key` on an iPhone and `install-runner`, an Apple ID signed in to Xcode > Settings > Accounts, whose team Xcode has saved (it does once a project's Signing & Capabilities tab has been opened), or `--team`; tested with Xcode 27.1 and a paid team. A free Apple ID (Personal Team) also signs the runner, untested here: its profile lasts 7 days, so `install-runner` is run again weekly, and the phone asks once to trust the developer (Settings > General > VPN & Device Management, needs internet). On macOS every command that targets a device runs `simctl` and `devicectl` too, to list simulators and iPhones ([Device selection](device-selection.md)).
- The first `ui-tree`, `tap`, `swipe`, `text` or `key` on a simulator compiles a small helper with the selected Xcode's `swiftc` (`DEVELOPER_DIR`, else the `xcode-select` one, else `/Applications/Xcode.app`) into `~/Library/Caches/karagoz/`. That takes a few seconds, happens again after an Xcode update, and the helper's folder is safe to delete. The `runner/` folder next to it holds karagoz's iPhone runner: after deleting it, run `install-runner` again, and while a runner started before is still up (up to 10 minutes), calls to that iPhone fail with `DEVICE_NOT_READY`.
- On a simulator, `tap`, `swipe` and `key` need Xcode 27 or newer: they go to the simulator's own input service, which older Xcodes do not have, and return `NOT_SUPPORTED` there. `text` loads Xcode's XCUIAutomation frameworks and puts the simulator in automation mode for the length of the call, as a UI test does; a UI test running on the same simulator makes it fail with `AUTOMATION_BUSY`. When the call ends, the simulator turns its app accessibility setting off; `text` writes it back if it was on, so later `ui-tree` reads still see apps.
